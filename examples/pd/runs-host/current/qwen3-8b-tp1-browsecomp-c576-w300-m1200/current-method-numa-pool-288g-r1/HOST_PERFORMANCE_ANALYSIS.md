# c576统一Host池：相对旧组慢在哪里

**后续复核更正**：下文Host占用和恢复延迟数字不变，但D→P占用增长不能全部解释为
有用请求积压。已确认30个budget结束的Agent仍保留139.46 GiB Host副本，正式窗口
平均约56.71 GiB。真正需要下一轮的窗口内Slow最终均有恢复记录，终止副本则应删除。
详见[Decode与Slow生命周期复核](DECODE_RUNNING_AND_SLOW_AUDIT.md)。

对照旧组`current-method-slow-congestion-1s-20260909-r1`。本次仅离线分析，没有修改
生产代码或启动新实验。统计各自正式1200秒窗口；引擎使用counter差分，Host完成日志
使用UTC时间和snapshot关联。日志秒级边界及重复事件处理可造成少量计数与前表不同。

## 结论与证据范围

不是P→Host DMA变慢，也没有复现几秒的动态Host注册阻塞。
新池显著增加P→D经Host传送的数据量；Host→D搬运计时速率略降，Host等待恢复变长。
同时新增加的Host恢复可行容量过滤使等待更多发生在Router确定P之前。
D持续Forward，但活跃Decode token/s下降。更多Host搬运与更长的实际轨迹共同存在；
没有隔离干扰的profile，不能把全部3.44%损失都归因于PCIe争用或Router。

## 四条Host传输

CUDA-event有效速率=该路径总GiB/总CUDA-event秒数，**不是带宽上限，也不是按1200秒
平均的速率**。event区间可能包含stream排队和资源竞争，不能当作纯硬件DMA极限。
整机墙钟流量=完成搬运的总GiB/1200秒；并行操作时两个口径不同。
字节数优先取snapshot日志bytes；Qwen3-8B TP1每token KV为147456字节。

| 路径 | 旧CUDA-event有效GiB/s | 新CUDA-event有效GiB/s | 旧整机墙钟GiB/s | 新整机墙钟GiB/s |
|---|---:|---:|---:|---:|
| D→Host | 6.99 | 9.67 | 1.54 | 1.77 |
| Host→P | 10.36 | 9.37 | 1.52 | 1.68 |
| P→Host | 12.48 | 13.56 | 4.65 | 10.78 |
| Host→D | 9.44 | 8.86 | 4.57 | 10.86 |

| 路径 | 旧平均CUDA-event / worker墙钟耗时ms | 新平均CUDA-event / worker墙钟耗时ms |
|---|---|---|
| D→Host | 248 / 298 | 205 / 259 |
| Host→P | 166 / 236 | 204 / 278 |
| P→Host | 116 / 135 | 145 / 171 |
| Host→D | 153 / 156 | 224 / 229 |

worker墙钟仅涵盖日志定义的传输工作段，不含在Host等待被选择的全部时间。
P→Host每次更久并不等于写入变慢：平均snapshot从约1.45增至1.97 GiB，大小增加约36%。
Host→D也不是纯粹大小效应：16k–32k tokens区间的event有效速率旧9.98、新9.00 GiB/s。
跨NUMA的Host→D比例约49.9%→48.5%，没有增加；本地传输速率也从10.31降至9.40 GiB/s，
因此不能把损失简单归咎于跨NUMA比例上升。

## 多出来的是大量P→D Host交通

P→Host完成约3844→6568次（+71%），搬运5576→12938 GiB（约5.45→12.64 TiB，+132%）。
P侧交付释放约9913→9885次，基本不变。即每100次P交付中，经Host的约39→66次。
代码中的Host容量拒绝会返回RETAIN_P，之后仍可通过普通Direct/D容量路径交付；
扩大Host后，更多请求能在grace后立即进入Host，而不是留在P等Direct。
这是容量改变带来的实际路径分布变化，不是新实现单次复制了两遍相同KV。

Host→D的累计CUDA-event秒数从约581增至1472秒（4张D合计，重叠区间不能当作
独占GPU时间相加）。因此“D Forward99.45%”不代表DMA没有影响Forward执行速度；
计算与copy stream可以并行，但不意味着数据访问完全无竞争。

窗口内registered_extent计时：旧均值0.036ms、P99 0.104ms；新0.038ms、P99 0.110ms，
新最大9.264ms。没有发现业务窗口内长时间注册可以解释本轮损失的证据。

## 真正的秒级等待在哪

以完成恢复的snapshot关联前后事件（未恢复项不纳入延迟均值）：

| 阶段 | 旧平均秒 | 新平均秒 |
|---|---:|---:|
| D→P offer → D2H启动 | 0.03 | 0.03 |
| P→D Host durable → 源P释放 | 0.32 | 0.34 |
| P→D Host durable → Host→D完成 | 8.44 | 15.20 |
| D→P Host durable → Host→P启动（含可能工具等待） | 5.45 | 9.59 |
| Host已durable且下一轮已到达 → Host→P启动 | 4.95 | 9.06 |
| 同一ready条件 → Slow恢复目标P确认 | 0.12 | 7.98 |
| Host→P完成 → Radix绑定释放Host事件 | 0.28 | 0.40 |

D→Host完成到D源释放均记录在同一秒，不支持“完成后还普遍扣住D几秒”的解释。
最后一行是秒级日志差值，不能据此断言精确到毫秒的延迟。

新Host恢复选择增加了完整workset可行容量过滤：若所有P均不足，保留Host所有权，
等待后续采样；这不在Forward线程执行。旧组主要先选P，再在P侧等待。
因此7.98秒并非一次选P函数运行了8秒，而是ready到最终成功确认P的经过时间；
不能把它全当作新增CPU开销。但整体ready→H2D也多了4.11秒，确实恢复更晚。

一个可核实的真实容量等待例子：snapshot `7ccb8c66408346e28d20f2d4a0981409:3`，
下一轮完整workset33332 tokens。相对测量开始293.52秒ready，465.67秒才确认P（172.15秒）。
ready附近四P引擎采样剩余tokens为384/8960/1728/12928；等待中379.60秒仍仅为
1216/5248/27264/6912，均不足33332。确认P附近出现25152/64320/18304/40576。
这说明至少这个长尾不是工具或网速慢，而是真有完整工作区不足。
这些是引擎采样，不包含所有未反映到采样的Router shadow扣减；另一些时刻采样看似
有空仍在等待，现有日志未保存每次候选拒绝的physical/shadow明细，不能排除过度保守。

## Host占用及阶段变化

旧P→D容量全机128 GiB，按queued→release事件重建平均约51.8 GiB，各P峰值30.3–31.7 GiB。
新P→D按broker物理日志平均202.0 GiB；两NUMA各自峰值191.5/191.9 GiB，已接近
保留对向96 GiB后的192 GiB单方向额度。容量扩大后队列确实容纳了更多内容。
新D→P平均77.4 GiB，没有接近全机方向可用上限；后期占用增多不能称为所有Slow及时恢复。

下表是新组正式窗口分段，两NUMA的Host均值相加，Forward/KV/running按每卡平均。

|---|---:|---:|---:|---:|---:|---:|---:|
| 0–300 | 30.1 | 168.7 | 92.3% | 50.9% | 82.4% | 54.7 | 4825.9 |
| 300–600 | 71.5 | 263.8 | 89.0% | 82.6% | 86.7% | 39.4 | 3532.5 |

| 900–1200 | 125.8 | 219.6 | 96.5% | 61.1% | 83.7% | 46.2 | 4189.4 |

低谷300–600秒，两端KV较满，D running较低，Host里大量P-ready KV等D；
600–900秒D running回到64.6，吞吐6109.5，P→D Host下降，证明队列可以排空。
最后300秒P Forward已96.5%，但D仍只有4189.4，不能把本轮损失单纯解释为P没持续算。
两池P→D都曾降到0，D→P分段均值则逐步上升；它们的趋势不能混为一谈。

完成集合平均轮次3.466→3.651，累计Prompt/Agent43511→47754，也增加了后续工作量。
引擎KV used/running含未完成传输、被pin等非running所有权，不能直接当作活跃请求平均上下文。

## 下一步应针对什么（本次未改动）

1. 优先核对Slow恢复的完整workset过滤：每次长期拒绝究竟是physical不足还是shadow
   已被真实分配覆盖却尚未扣回。应复用压力采样并按异常采样记录，不能新增高频同步查询。
2. 不要仅扩大Host或增加DMA并发。当前最明显的新负担是P→D经Host的字节量增加132%；
   若要隔离其影响，需要固定路由选择/负载，单独比较容量，或按同等batch/上下文区间
   比较有无Host→D复制重叠时的Decode速度。当前数据仅支持相关性，不足以精确归因。
3. 无需以本轮证据去重构P→Host写入、延长Direct等待或改动Forward状态机：
   单次写入速率未下降、启动及源释放链路没有显著恶化。
